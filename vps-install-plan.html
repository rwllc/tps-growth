What ClaudeClaw Actually Needs

Grounded in the Repo, Not the Internet

Pulled directly from README.md's "Cloud deployment (advanced)" section and scripts/agent-service.sh — this is what's actually documented and shipped, not general VPS folklore.

Baseline requirements from repo

  • Node.js 22 or 24 (LTS) + git
  • Claude Code authenticated — the hard part on a headless box, see below
  • 512 MB RAM minimum, 1 GB+ recommended (each query spawns a Claude Code subprocess)
  • Outbound access to api.telegram.org and the Anthropic API (plus any optional integrations enabled)
  • A writable persistent filesystem for store/claudeclaw.db (SQLite/SQLCipher)

The good news about a real VPS from repo

The README's cloud-deployment warnings are mostly aimed at ephemeral container platforms (Railway, Fly, Render) that wipe the filesystem on every redeploy. A real VPS — a plain Ubuntu/Debian box with a persistent disk — doesn't have that problem by default. It behaves like "a Linux machine," so the standard Linux install path applies (npm run setup → systemd --user service), not the container workarounds.

The One Real Blocker

Headless Auth: Claude Code Can't Open a Browser

claude login is the normal path and it wants an interactive browser OAuth flow. A VPS has no browser. This is the actual failure mode most people hit on a first VPS attempt — worth betting that's close to what went wrong with openclaw before, even though that's a different codebase.

Beyond the Official Docs

VPS-Specific Gotchas to Rehearse

These aren't in the ClaudeClaw README — they're standard Linux-VPS operational issues that bite first-time deployments generally. verify on practice box

systemd --user dies on logout

The setup wizard installs a user systemd service. By default, user services stop when your SSH session ends — the opposite of "always on." Fix: loginctl enable-linger <username> on the VPS so user services keep running with no session attached. Easy to miss, easy to test for.

Native module build fails

better-sqlite3 is a native Node module. A minimal/fresh Ubuntu image often lacks the compiler toolchain. Fix: apt install build-essential python3 make g++ before npm install if no prebuilt binary matches the VPS's OS/arch.

Dashboard exposure

The dashboard link embeds a password in the URL — treat it like a credential, never screenshot/share it. Recommended: Cloudflare Tunnel (free, no inbound ports opened) to reach it remotely, optionally layered with Cloudflare Access for a login wall. A raw VPS has no platform-provided public URL the way Railway/Fly do, so skipping the tunnel isn't an option here the way the README allows for those platforms.

The box is now internet-facing

Unlike Bob's home Mac, this VPS has a public IP. Baseline hardening: SSH key-only auth (disable password login), ufw firewall (only 22/SSH inbound; the dashboard goes out through the tunnel, not an open port), fail2ban, and unattended OS security updates.

Back up the key, not just the database

store/claudeclaw.db is SQLCipher-encrypted with DB_ENCRYPTION_KEY from .env. A backup of the database file without the key is unrecoverable. Back up both, together, off the VPS.

Remote access for Bob

Needs either an SSH key added to the box (ask Doug/whoever provisions it to add Bob's public key) or Tailscale for a simpler private-mesh alternative to managing SSH/firewall rules directly. Either way — this is Doug's VPS, so who gets access and at what privilege level is his call to confirm, not an assumption to build around.

Rehearse Before Touching Doug's Box

Practice-VPS Plan

You've never done a ClaudeClaw VPS install before — the one openclaw attempt doesn't transfer directly since it's a different codebase with different auth and service mechanics. Treat a cheap throwaway VPS as mandatory rehearsal, not optional caution.

  1. Spin up a disposable droplet. DigitalOcean, Linode/Akamai, Vultr, or Hetzner — any plain Ubuntu LTS image, smallest size that meets the 1GB-recommended RAM bar. cost estimate below, verify at signup
  2. Full install, start to finish: clone the repo, npm run setup, pick the auth method from the table above, get the Telegram bot responding.
  3. Install as a systemd --user service and immediately run loginctl enable-linger — then close the SSH session and confirm the bot still responds on Telegram with the session gone.
  4. Reboot test. Reboot the droplet from the provider's console, wait, confirm the service comes back on its own without manual intervention.
  5. Crash-restart test. Kill the node process directly (kill -9) and confirm systemd's Restart=always brings it back within ~10 seconds.
  6. Dashboard over Cloudflare Tunnel — confirm remote access works from Bob's phone/laptop away from the VPS network.
  7. Tear it down once everything above passes — it's a $10-20 rehearsal, not a thing to keep paying for.
